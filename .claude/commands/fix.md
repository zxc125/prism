# /fix — 修复短路径

## 输入

bug：$ARGUMENTS

## 你的角色

你是修复者。这不是新需求，是既有产出的 bug 修复——走轻量路径，不重走 `/cycle`。

## 流程

### 1. 定位归属 P

根据 bug 涉及的文件/功能，定位它属于哪个 P 阶段：
- 读 CLAUDE.md 进度表判断
- 读对应 `docs/阶段路径/Pxx-*.md` 确认是该 P 的范围

### 2. 升格判断（gate — 先判断要不要走 /fix）

**以下任一条件命中 → 停止 /fix，建议升格 `/cycle` 走新 P**：
- 跨多个 P 阶段（如同时改 P7 bundle + P8 server + P9 限流）
- 动 CLAUDE.md「四条锁定决策」
- 改 bundle 契约（`prism-session` 格式）
- 改对外 API 签名（SDK / Tauri command / HTTP API）
- 改动面超过单 P 局部修

如果命中升格条件，向用户说明原因，建议改走 `/cycle`。

### 3. 复现（gate — 必须留档）

**必须先复现 bug**，写下复现步骤：
- 触发条件
- 预期行为 vs 实际行为
- 涉及的文件/函数

如果不能复现，先调查到能复现再修。**不留复现路径的修复 = 不完整**。

### 4. 修复

定位根因 → 改最小范围（不要顺手重构无关代码）→ 跑该 P 已有测试：
- Rust 改动 → 受影响 crate `cargo test`
- 前端改动 → `pnpm build`
- 参照 `docs/测试/Pxx-测试流程.md` 的相关场景验证

### 5. 回写文档（两个地方）

**(a) 原 P 文档修复记录段** — 在 `docs/阶段路径/Pxx-*.md` 的 `## 修复记录` 段追加一行：
```
- YYYY-MM-DD <commit short hash> <一句话修复说明>
```
不改历史行，只追加。如果 P 文档没有「修复记录」段，按模板补一个。

**(b) CLAUDE.md 验证列** — 如果 `cargo test` 数字变了（如从 53 → 54），更新进度表该 P 行的「验证」列数字。**不加新 P 行**（P 阶段是范围单位，不是时间单位）。

### 6. 呈现结果

汇总：复现路径 + 修复 diff + 文档回写位置，请用户确认。

## Gate（过关条件）

- [ ] 升格判断通过（确认是单 P 局部修）
- [ ] 复现路径留档（触发条件 + 预期 vs 实际）
- [ ] 该 P 已有测试通过
- [ ] 原 P 文档「修复记录」段已追加
- [ ] CLAUDE.md「验证」列数字已更新（如变化）
- [ ] 用户确认

## 注意

- **不要借 fix 顺手做大重构**——那会扩大影响面，应该升格 `/cycle`
- **不要新建 P 文档**——修复回写到原 P 文档，上下文在那里最完整
- **不要新建 `docs/修复/` 目录**——分散反而难查
- 如果 fix 过程发现原方案有系统性问题（不是孤立 bug），停下来建议开新 P
