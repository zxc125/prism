# 大文件回放性能 决策

> 2026-09-10 P19 需求评审（/spec）产出。上一轮 `c2d159b` 已止血 Rust 侧主线程冻结；本决策处理剩下的回放侧可用性问题。实现流水账见 [docs/阶段路径/P19-大文件回放性能.md](../阶段路径/P19-大文件回放性能.md)。

## 背景（实测基线）

本地真实会话 `1789022053209`（外部应用 stellar-tradehub 导入）：

| 指标 | 实测 |
| --- | --- |
| 体积 / 段数 / 事件数 | 180.7 MB / 27 段 / **24,277 事件** |
| 按类型分摊 | Incremental(type3) **135.7MB / 75.1%** · FullSnapshot(type2) **42.9MB / 23.7%**（≈1.6MB/段，共 27 份）· Plugin(type6) 2.0MB / 1.1% |
| Rust parse + serialize（debug） | 13.8s（已由 `c2d159b` 移出主线程） |
| JS `JSON.parse`（node/V8 复刻） | **1.0s**，heap **+1042MB**，rss 1165MB |

结论：**体积由「每段一份全量快照 + 大量增量 mutation」构成，事件条数很少**（平均每事件 7.4KB）。因此成本不在遍历事件，而在**搬运与解析字节**、以及**每段一次的全量 DOM 重建**。

## 范围决策

- **优先级：本阶段为当前最高优先级**（2026-09-10 用户确认「按性能优先级最高做」）。含义有三：① 性能问题优先于任何新功能；② 本阶段内的取舍一律以性能为先（可读性、抽象美感、API 简洁让位于实测收益）；③ Phase A（交互止血）与 Phase C（Replayer 生命周期）属「可用性阻塞」，先做且不可裁剪；Phase D（录制档位）可裁剪。

- **只治回放侧，不治录制产物格式**：bundle 契约（`prism-session` v1）、Sink 六方法接口、交错事件模型（type:6 同流）、绝对时间戳对齐**全部不动**。理由：老会话必须继续可播，跨进程/跨机迁移契约不能因性能改版。
- **Rust 侧主线程冻结不在本 P**：已由 `c2d159b`（P17 修复记录第三批）解决，本 P 只处理其剩余部分（JS 侧加载与回放）。
- **与 P14「回放侧零改动」的边界重述**：P14 那条约束的语义是「**录制档位变化不得要求回放侧感知**」（新档位产出的数据，旧回放链路零改动即可消费）；P19 改的是**回放性能策略本身**，不改任何数据消费语义与格式。二者不冲突，但本 P 触及 `usePlayer`/Player 组件，**必须在 P 文档显式声明，避免被读成推翻 P14**。
- **不承诺「打开秒开」**：本 P 的验收是「大文件可交互、播放流畅」，不是「零等待」。180MB 的字节搬运与 DOM 重建有物理下限。

## 技术路线决策

- **读路径分段化（D1）**：新增 `read_session_meta`（元信息 + 段索引）+ `read_segment`（单段事件），`read_session` 保留兼容但 Player 不再使用。理由：沿用 P7 已确立的尺子——「大 bundle 走 `import_session_path`，不过 IPC 大字符串」；读方向此前没有对应物，是同一原则的补全。段索引只需读每段**第一行**（Meta 事件含 viewport w/h），O(段数) 而非 O(事件数)。
- **段事件走 raw IPC（D2）**：`read_segment` 不做 `serde_json::Value` 往返——jsonl 每行本身是合法 JSON，直接拼 `[l1,l2,…]` 成字符串，用 `tauri::ipc::Response` 返回 UTF-8 字节，JS 侧 `TextDecoder` + `JSON.parse`。理由：实测 Rust 侧建 `Value` 树峰值 RSS **2.9GB**，纯属中间态浪费；这同时兑现 P17「不在本阶段」清单里预留的「二进制 IPC」。
- **Replayer 按需创建与回收（D3）**：只为「即将活跃」的段建 Replayer（预取窗口内），不活跃超阈值则 `destroy()` 并释放事件数组。理由：现状 attach 时对 27 段全部 `new Replayer` + `pause(0)`，而 rrweb 的 `pause(offset)` 内部是 `play(offset)` + `PAUSE`——白白调度全部未来事件并构建整棵 DOM；27 次全量 DOM 重建是打开卡顿的主体。注意：**删除 `pause(0)`，改为段首次活跃时定位一次**。
- **废弃播放中漂移阈值纠偏（D4）**：删除 `DRIFT_THRESHOLD`/tick 内 `play(expect)`，对齐只发生在**段激活 / 用户 seek / 暂停 / 切倍速**四个时点。理由：rrweb 的 `play(offset)` 在非 paused 状态会先发 PAUSE 再 PLAY，等于一次**完整的 O(段首→offset) 全量同步重放**；在大会话上它阻塞主线程数百 ms → 下一 tick 测到更大漂移 → 再次纠偏，构成正反馈。段边界本身就是天然同步点。
- **正式证伪「方案 A 主时钟步进」（D5）**：`rrweb-recording` skill 里写的「主 RAF 每帧 `replayer.pause(offset)` 步进驱动 → 彻底零漂移」在本项目依赖的 rrweb 2.1.1 上**不可行**——每帧 `pause(offset)` 就是每帧一次全量 cast，比现状更糟。本决策取代该条，并回写 skill。侧槽允许有界漂移，只保证 spotlight 主窗口精确。
- **seek 拖动只预览、松手才提交（D6）**：`@input` 只更新预览播放头，`@change` 才真正 seek。理由：el-slider 拖动期间每个 pointermove 都会触发一次 `seek()` → 每个活跃段一次全量重放，拖 2 秒 = 上百次。
- **诊断信号流虚拟化（D7）**：定高虚拟滚动（行为单行 `nowrap`，行高固定）+ `activeSigIdx` 改二分 + 播放中不做 `scrollIntoView`。理由：现状 `v-for` 渲染全部信号行、每 50ms 线性扫描一次、每次索引变化强制布局并滚动——三者叠加在播放中持续吃主线程。
- **播放循环收敛（D8）**：`syncVisibility` 从「每 tick O(labels×segs) 双层循环 + 写 `style.display`」改为「活跃集合变化时才 diff 更新」；播放头推进改 `requestAnimationFrame`。
- **`checkoutEveryNms` 走档位、且需实测后定（D9）**：rrweb 2.1.1 的 `record()` 对该项**无默认值**，本项目从未设置 → 每段只有段首一个快照，`discardPriorSnapshots` 只能 slice 到段首，每次 seek 都要重放该段全部增量。开启周期快照可把 seek 成本上界压到 ≤checkout 间隔，代价是体积上升（本次数据：每份快照 ≈1.6MB）。**倾向按 P14 档位暴露、默认值待实测体积增幅后定。**（2026-09-10 延后：A/B/C 落地后 seek 频率已收敛，价值待运行时体感验证，采纳门不变——见 P19 文档「不在本阶段」。）

## 边界决策

- **不动 bundle 契约**：`format/version/segments` 结构不变。分段读是**读 API** 的事，与产物格式解耦。
- **对外 API 只增不改**：console 新增 2 个 command、observer-server 新增 2 条路由、`Backend` 接口新增 2 个方法；`read_session` / `GET /sessions/:id` 签名与行为保持不变（导出、旧消费者、浏览器模式未迁移前都能跑）。
- **浏览器模式不对齐 raw IPC**：`HttpBackend` 天然是 HTTP 分段传输，无需 raw 优化；`Backend` 接口设计必须让 Tauri 与 HTTP 两条路都能实现（分段方法与 `Response` 无关）。
- **不做 worker 化**：不把 rrweb Replayer 搬进 Web Worker（rrweb 依赖 DOM，收益与风险不成比例）。

## 未做（留后续）

- **二进制事件编码**（protobuf/msgpack 类）：本轮先用「jsonl 直拼 + raw IPC」吃掉 Value 树与二次转义，若仍不够再议。
- **位置精确回放（原「方案 C」）**：录制窗口 x/y/w/h、按原位摆放——与性能无关，仍是独立候选。
- **录制端 `inlineStylesheet` 开关**：关掉可显著减体积（本次快照含大量内联 CSS），但会牺牲回放保真度，不做。
- **server 端读路径的分段端点消费方**：`HttpBackend` 迁移到新端点可后置，先保证端点存在且契约稳定。
