# 离线导出与云端部署（方案评审稿）

本文档回应两个能力诉求，给出最佳实践方案供评审：

1. **离线闭环**：用户在自己的系统自行录制 -> 导出文件 -> 上传到本系统回放（不依赖 console 实时在线）。
2. **云端私有部署**：将本系统私有部署到云端，不走本地 server 传输。

---

## 1. 核心论点：bundle 是平台的统一 interchange

现状已有两种数据形态：

- **存储形态**：`recordings/<sessionId>/{session.json, windows.jsonl, segments/<label>#<n>.jsonl, annotations.jsonl}`。
- **bundle 形态**：`prism-session`（[lib.rs](../../src-tauri/src/lib.rs) `build_export_bundle`），且已是存储形态的忠实序列化，带 `version: 1`。

```json
{ "format": "prism-session", "version": 1, "exportedAt": ...,
  "session": {...}, "windows": [...], "segments": {"web#1": [...]}, "annotations": [...] }
```

**方案把 bundle 提升为「会话跨进程/跨机迁移的唯一契约」**。三条传输拓扑全部收敛到它：

| 拓扑 | 路径 | 现状 |
|---|---|---|
| 本地文件分享 | export -> 文件 -> import | ✅ 已有（P6） |
| 本地 server 实时流 | HttpSink -> /ingest -> 存储 | ✅ 已有（P4） |
| 离线录 + 上传 | IndexedDBSink -> bundle -> import/upload | ❌ 缺产出端 |
| 云端 server | HttpSink -> 云端 /ingest -> 云端存储 | ❌ 缺服务端 |

后两条是本次要补的。只要 bundle 契约统一，**离线 bundle 既能喂本地 import，也能 POST 给云端 upload 端点**，一次产出、三种投递。

## 2. 分层架构（在现有基础上 minimal 重排）

```
L1 采集层   SegmentRecorder + 信号 hook（不动）
L2 Sink 层  HttpSink(实时) / IndexedDBSink(离线,补全) / [未来] TauriLocalSink
L3 存储层   tauri-plugin-observer::storage（已与 AppHandle 解耦，原样抽出）
L4 服务层   observer-server crate（ingest + 读 API + import/export，可绑 127.0.0.1 或 0.0.0.0）
L5 分析层   console（Tauri app）+ Backend 抽象（Local=invoke / Cloud=HTTP）
```

关键：**不 fork 产品**。同一份 storage lib、同一份 server lib、同一份 bundle 规范、同一个 console。部署拓扑是配置开关，不是代码分支。本地优先仍是默认；云端是 opt-in 拓扑。

## 3. 需求一：离线采集 -> 导出 -> 上传 -> 回放

### 3.1 设计

`Sink` 抽象的价值在这里兑现：离线 = 同一个 `SegmentRecorder` 换一个 `IndexedDBSink`，采集逻辑零改动。

补全 [sinks.ts](../../packages/observer-sdk/src/sinks.ts) 的 `IndexedDBSink`（现状是写-only 骨架，留 `// TODO 独立回放的读取路径待补`）。 IndexedDB schema：

```
db: observer-sessions
  sessions:   key=sessionId -> { meta, startedAt, endedAt }
  segments:   key=segmentId -> { sessionId, label, startedAt }   index=[sessionId]
  events:     auto -> { segmentId, event }                       index=[segmentId]
  lifecycle:  auto -> { sessionId, event }                       index=[sessionId]
```

读路径：按 sessionId 取 meta + 全部 segments + 按 segmentId 分组 events + 全部 lifecycle -> 序列化成 bundle。

### 3.2 SDK 新增 API

```ts
// 离线录制（不传 endpoint）
recordOffline(opts: { appId, signals?, meta? }): Promise<OfflineController>

interface OfflineController {
  stop(): Promise<OfflineSessionId>            // 停录、标记 endedAt
  export(id?): Promise<Bundle>                 // 序列化成 prism-session bundle
  download(id?): Promise<void>                 // export + 触发文件下载
  list(): Promise<OfflineSessionMeta[]>        // 列出本机离线会话
  clear(id?): Promise<void>                    // 清理
}
```

`recordOffline` 内部把 `SegmentRecorder` 接到 `IndexedDBSink`，与现有 `init()`（接 `HttpSink`）并列。

### 3.3 TS 侧 bundle builder/parser

新增 `packages/observer-sdk/src/bundle.ts`：`buildBundle(sessionData)` / `parseBundle(bundle)`，对齐 Rust `build_export_bundle`/`write_import_bundle` 的字段。复用点：

- SDK 离线 export（产出）。
- console 前端 import（客户端先 parse 校验，再 invoke 或 HTTP upload）。
- console 前端 export（可逐步迁 TS，与 Rust 实现共享规范 + 测试 fixture）。

### 3.4 console 导入侧改造

- 新增 `import_session_path(path: String)` 命令：Rust 侧读文件，避免把超大 JSON 字符串过 Tauri IPC（现状 `import_session(content: String)` 整串过 IPC，大 bundle 有内存/IPC 压力）。
- 前端用文件选择器拿到路径后调 `import_session_path`。
- 保留 `import_session(content)` 给云端 HTTP upload 与小文件路径。

## 4. 需求二：云端私有部署

### 4.1 与锁定决策的关系（必须先理清）

锁定决策 #1「本地优先 - Tauri App 当分析台，零云依赖，不建云后端 RUM」看似与云端冲突。但**私有云自托管 ≠ 公有云 RUM SaaS**：

- 决策 #1 拒绝的是「成为 SaaS RUM 厂商、数据上第三方云」。
- 私有云自托管是用户 own 自己的数据、自己运维，零厂商云依赖，**精神与 #1 一致**，只是 server 跑在哪台机器上的区别。

因此方案不推翻 #1，而是引入「**自托管 server**」作为 opt-in 拓扑：默认仍本地优先（console 内嵌 server，绑 127.0.0.1）；显式配置云端 endpoint 后切到自托管 server。决策 #2「统一走 HTTP sink -> console 本地 server」顺势扩展为「-> 本地或自托管 server」（HttpSink 的 `endpoint` 本就可配任意 URL）。

### 4.2 服务端抽取：observer-server crate

存储层已与 AppHandle 解耦（`append_*`/`create_session`/`finalize_session` 只吃 `&Path`，`handle_route` 只吃 `root: &Path`，见 [ingest.rs](../../src-tauri/src/ingest.rs) 测试）。抽取基本是重新打包：

新 crate `observer-server`（或在 plugin 内加 `server` feature + binary）：

- 复用 `tauri-plugin-observer::storage` 的落盘函数。
- 复用 `handle_route` 的 ingest 路由（`/ingest/*`）。
- 新增**读 API**：`GET /sessions`、`GET /sessions/:id`、`GET /sessions/:id/annotations`、`GET /sessions/:id/export`。
- 新增 **upload**：`POST /sessions/import`（接收 bundle，云端版 `import_session`）。
- 配置：`bind`（`127.0.0.1` 或 `0.0.0.0`）、`dataDir`、`auth`、`tls`。

console 的 [ingest.rs](../../src-tauri/src/ingest.rs) 内嵌 server 退化为「`observer-server` 绑 127.0.0.1、指向 appDataDir」的薄封装，**同一份代码**。

### 4.3 console 的 Backend 抽象

console 前端现状直接 `invoke("list_sessions")` 等。云端需要走 HTTP。引入接口：

```ts
interface Backend {
  listSessions(): Promise<Session[]>
  readSession(id): Promise<SessionData>
  listAnnotations(id): Promise<Annotation[]>
  saveAnnotations(id, anns): Promise<void>
  updateSessionMeta(id, meta): Promise<void>
  exportSession(id): Promise<Bundle>
  importBundle(bundle): Promise<SessionId>
  deleteSession(id): Promise<void>
}
```

两个实现：`TauriBackend`（现有 invoke）+ `HttpBackend`（HTTP 调云端）。设置页切换，默认 Tauri。**录制 Sink 与 Backend 正交**：录制仍走 HttpSink（指向本地或云端），Backend 只管读/管理。

> 关键取舍：**不做浏览器版 web console**。Tauri app 作为「云端 server 的桌面客户端」即可覆盖私有云场景（装一次 desktop client，连云端 endpoint）。浏览器版 console 是更大产品决策，列为可选 Phase D，仅当「不许装客户端」时才做。

### 4.4 鉴权与多租户

- **鉴权**：现状 ingest token 是单一共享 bearer（本机回环够用）。云端升为**每租户 API key**，`Authorization: Bearer <key>`，server 映射 key -> tenantId + appId 集合。
- **多租户存储**：`recordings/<tenantId>/<sessionId>/`（或 tenant 前缀）。`session.json` 已有 `appId` 字段。
- **TLS**：server 绑 0.0.0.0 + 反代（nginx/caddy）终止 TLS，或内置 rustls。私有云建议反代，简单。
- **单租户起步**：Phase B 先做单租户（一个 key、扁平目录），Phase C 再加多租户/配额/保留策略。

## 5. 边界问题清单（跨两个需求）

| # | 边界问题 | 影响 | 处理 |
|---|---|---|---|
| B1 | **导入路径穿越（安全）** | 高 | `write_import_bundle` 现直接用 bundle segment key 当文件名，无净化。**必须**校验 `^[A-Za-z0-9_-]+#[0-9]+$`，拒绝 `..`/分隔符。云端不可信上传为高危，本地也应修。 |
| B2 | **bundle 体积** | 高 | DOM 录制 5min 可达 10–50MB，多窗口更大。export 用流式序列化（ReadableStream -> Blob），不全量拼字符串；console import 走 `import_session_path` 读文件，不过 IPC 大字符串；传输 gzip。 |
| B3 | **存储压缩** | 中 | segments 是高压缩比 JSON。落盘 + bundle 内 gzip（`Content-Encoding` / `.jsonl.gz`）。replay 侧透明解压。 |
| B4 | **PII / 敏感数据** | 高 | network body / console args / DOM 文本可能含 token、密码、邮箱。export 前提供 redaction 钩子（正则 scrubber），network body 默认导出时剥离；上云前必经 scrub。 |
| B5 | **bundle 完整性与版本** | 中 | 已有 `version: 1`。import 侧做 schema 校验 + 原子导入（写临时目录成功后 rename，不留半成品）。 |
| B6 | **大 bundle 的 IPC** | 中 | 见 B2，新增 `import_session_path`；`export_session` 大bundle 走文件路径返回而非整串。 |
| B7 | **并发写** | 中 | 云端多客户端并发上报。`unique_session_id` 已 loop 避碰；段追加用 append；跨会话天然隔离。租户级写限流。 |
| B8 | **离线存储配额** | 中 | IndexedDB 浏览器可回收。长录制约上限提示 + 旧会话淘汰策略；`beforeunload` 不保证 flush 巨量缓冲，离线模式下事件即时落 IndexedDB（非批量缓冲）缓解。 |
| B9 | **replay 资源保真** | 中 | rrweb 录 DOM 不录外部 CSS/字体/图片。离线录的页面在 console 回放时外部资源可能 401/404。文档化 + 缺失资源告警；可选「内联关键样式表」。不试图完全解决。 |
| B10 | **时钟与时间戳** | 低 | 绝对 epoch ms，单会话单源无漂移。跨会话不合并，无问题。 |
| B11 | **多窗口离线（Tauri plugin）** | 中 | Q1 先只做 web SDK 单 tab。Tauri plugin 离线 = plugin 写外部 app 自己的数据目录 + Rust export 命令，列为 Phase A 之后。 |
| B12 | **上传鉴权与归属** | 中 | 离线 bundle 上传云端时，uploader 凭 key 鉴权，bundle 落入对应 tenant；`session.json.appId` 须与 key 授权的 appId 集合匹配，否则拒。 |
| B13 | **保留与配额** | 中 | 云端需保留策略 + 每租户磁盘配额（SettingsView 文档提及未建）。Phase C。 |
| B14 | **annotations 一致性** | 低 | bundle 已含 annotations。导入重建后 id 保持；标注与事件流分离，无跨流一致性问题。 |

## 6. 新增功能清单

**需求一（离线闭环）**
1. 补全 `IndexedDBSink`：schema、读路径、`endSession` 标记。
2. SDK `recordOffline()` / `OfflineController`（stop/export/download/list/clear）。
3. `packages/observer-sdk/src/bundle.ts`：TS `buildBundle`/`parseBundle`，对齐 Rust 规范。
4. bundle 规范文档（字段、版本、校验规则）+ 共享测试 fixture。
5. console `import_session_path` 命令 + 文件选择器导入；大 bundle 路径化。
6. export 侧 redaction 钩子（B4）。

**需求二（云端）**
7. `observer-server` crate：ingest + 读 API + import/export 端点，可绑 0.0.0.0。
8. console `Backend` 抽象（TauriBackend / HttpBackend）+ 设置页切换。
9. 鉴权：每租户 API key + appId 集合校验（B12）。
10. 云端 `POST /sessions/import` bundle upload 端点。
11. **安全加固**：import 路径净化（B1）、大小/数量限制、原子写、流式 parse。

**跨切**
12. segments gzip（落盘 + bundle + 传输，B3）。
13. 保留策略 + 配额（Phase C，B13）。
14. replay 缺失资源告警（B9）。

## 7. 不做什么（scope 纪律）

- **不做浏览器版 web console**。Tauri-as-cloud-client 覆盖私有云；web console 列 Phase D，仅当明确需要「零安装浏览器访问」。
- **不做 OAuth / 复杂多租户**。Phase B 单租户 + API key 足够；OAuth/SSO 等真有多租户需求再上。
- **不 silently 改锁定决策**。云端是 opt-in 自托管拓扑，本地优先保持默认；明确「自托管 ≠ SaaS RUM」。
- **不试图解决 replay 外部资源保真**。文档化 + 告警，不内联全量资源。
- **Q1 先只做 web SDK**。Tauri plugin 离线延后（B11）。

## 8. 分阶段建议

| 阶段 | 内容 | 体量 | 决策冲突 |
|---|---|---|---|
| **A** | IndexedDBSink 补全 + SDK 离线 API + TS bundle + `import_session_path` + import 路径净化（B1）+ redaction 钩子 | 中 | 无 |
| **B** | `observer-server` crate 抽取 + console `Backend` 抽象 + 单租户 API key + 云端 upload 端点 + TLS（反代） | 中大 | 显式 opt-in 放宽 #1 |
| **C** | 多租户存储 + 配额/保留 + segments gzip + 服务端 redaction | 中 | 无 |
| **D**（可选） | 浏览器版 web console | 大 | 无 |

**A 与 B 的交汇点**：A 产出的 bundle，B 的 `POST /sessions/import` 直接消费。所以 A 先做不浪费，且 A 独立有价值（本地文件离线分享，零决策冲突）。建议**先落 A，评审通过后接 B**。
