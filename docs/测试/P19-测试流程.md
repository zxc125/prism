# P19 测试流程

> P19（大文件回放性能）本地测试指南。覆盖 6 条验收线：首屏载荷、播放同步、seek 交互、信号流虚拟化、按需加载与回收、录制档位（可裁剪）；外加前序阶段回归（P14/P16/P17/P18 不退化）。
>
> 主要验证数据：本机真实会话 `1789022053209`（外部应用 stellar-tradehub 导入，172 MiB / 27 段 / 24,277 事件 / 27 个 `shown`、**0 个 `hidden`**、session.json 无 `endedAt`）。这份数据是 P19 的"压力样本"，也是多个设计假设被推翻的地方（见 P19 文档「关键陷阱」）。

## 场景 1：大文件首屏载荷（读路径分段化）

**目标**：打开会话不再一次搬运 180MB。

**步骤**：
1. 从会话列表点开 `1789022053209`。
2. 观察时间轴与窗口槽位是否**立即可见**（不再长时间白屏）。

**预期**：
- 首屏只有一次元信息读取：`read_session_meta` 返回 **14,858 字节**、Rust 侧 **≈30 ms**（27 段索引）。
- 段事件在播放头进入预取窗口（3 s）时才逐段拉取，单段最大 36.5 MB（main#11）。
- 旧路径对照（同一数据、release）：`read_session` parse 0.92 s + serialize 0.91 s、峰值 RSS 3.27 GB。

**可选的量化验证**（DevTools Console，播放前）：
```js
// 首屏后不应出现 180MB 级别的解析；观察 Performance 面板里 read_session_meta / read_segment 的调用次数
performance.getEntriesByType("measure").length; // 无强制要求，仅作观察
```

## 场景 2：播放同步（废弃漂移纠偏 + 活跃段去重）

**目标**：播放中不再出现周期性全量重放（这是"卡顿 + 倍速下拉框开了又关"的根因）。

**步骤**：
1. 打开样本会话，点播放，让它跑 30 s 以上。
2. 播放中切换倍速（0.5x / 1x / 2x / 4x）数次。
3. 播放中点击倍速下拉框，确认弹层开合正常。

**预期**：
- 播放期间**不调用** `Replayer.play()`（只在段激活/seek/暂停/播放时调用）。
- 倍速下拉框不再"开了又关"（该症状是主线程饥饿的副产品）。
- 各窗口画面基本同步；侧槽允许有界漂移（D4 决策：不再用纠偏换同步，因为纠偏=全量重放）。

**关键回归点**：样本会话 0 个 `hidden`，若 `activeAt` 未按 label 去重，tick 会对同一 label 的全部历史段每 50 ms 调一次 `play()`（旧实现 13 次/tick）。观察方式：Performance 面板录制 10 s 播放，`Replayer.play` 调用次数应为 0。

## 场景 3：拖动进度条（松手才提交）

**目标**：拖动期间不触发任何 Replayer 工作。

**步骤**：
1. 暂停态拖动进度条，松手。
2. 播放态拖动进度条，松手。

**预期**：
- 拖动过程中播放头与时间码跟手，但**不发生 seek**（无 `Replayer.pause(offset)` 调用）。
- 松手后一次性跳转；**播放态松手后画面继续播放**（不得停在原地）。
- 旧行为对照：el-slider 的 `@input` 每个 pointermove 触发一次全量重放。

## 场景 4：诊断信号流（虚拟滚动 + 全量信号）

**目标**：信号条数与渲染行数解耦，且信号覆盖全库（不依赖段是否已加载）。

**步骤**：
1. 打开样本会话，切到「信号」tab。
2. 快速滚动信号列表。
3. 切换过滤条件（全部 / console / network / error）。
4. 点击任意信号行，确认播放头跳转。

**预期**：
- `document.querySelectorAll('.sig-row').length` ≈ 视口行数 + overscan（与信号总数无关）。
- 信号总数来自**全库** `GET /sessions/:id/signals`（Rust 侧只回 `type:6` 行），不随段加载增减、不重复。
- 播放中列表**不自动滚动**；暂停/点击/seek 时目标行进入视口。
- 行高按实测值换算（真实 30px vs 兜底 27px），滚动位置与内容对应。

## 场景 5：按需加载与回收（多段切换）

**目标**：Replayer 数量有上界，且不出现「加载→销毁」抖动。

**步骤**：
1. 打开样本会话，从头播放到结尾（约 27 段），期间观察窗口槽位切换。
2. 中途 seek 回早期位置，再 seek 到末尾。

**预期**：
- 同时存在的 Replayer ≤ 6（`MAX_LIVE_SEGMENTS`）；已过去的段被回收。
- 回收后的段**不会**在下一 tick 被立即重新加载（`isPast` 用 `lastTs` 判定，而不是依赖可能缺失的 `hidden`）。
- 段切换无白屏闪烁；未就绪段显示「载入中」占位，加载失败显示「载入失败」并在退避后重试（≤3 次）。

## 场景 6：录制档位（Phase D，可裁剪）

**目标**：`checkoutEveryNms` 能以可接受的体积代价降低 seek 延迟。

**步骤**：
1. 先跑体积实测（见 P19 实施顺序 4.0）：同一场景下开/关 checkout 各录一次，比较文件体积。
2. 体积增幅 ≤30% 才采纳；否则**整段裁剪**并在 P19 文档注明。
3. `full` 档必须保持零 diff（不写 `checkoutEveryNms` 字段）。

## 独立复核基线（两轮 fresh subagent）

复核用「把当前 `usePlayer.ts` 逐字复制到 /tmp 打桩驱动」+「真实会话索引喂入」的方式取得可执行证据，
对比对象是 `git show HEAD:` 的旧版本：

| 指标 | 旧实现 | 现实现 |
|---|---|---|
| `play()` 调用 / 100 tick（播放头在 main#11 段内） | 1684 | **2** |
| `play()` 调用 / 全片 11,165 tick | 116,069 | **27**（每段激活一次） |
| 27 段在全片播放中的加载次数 | main#11 反复重载 | **各恰好 1 次** |
| 信号条数（回收后重载场景） | 膨胀到 29,009（23,791 重复） | **无重复** |

真实数据接口基线（release，`/tmp` 直调 Rust）：
- `read_session_meta`：27 段 /**14,858 字节** / **≈31 ms**
- `read_segment_json`：27 段合计 **24,277 事件** / 180,661,276 字节 / 1.32 s（含逐段解析）
- `read_session_signals_json`：**1.95 MB** / 97 ms（占全量 1.13%，其中 9,797 条为真 `type:6`，另有 200 条含嵌套 `"type":6` 的 DOM 事件由 JS 侧按解析后 `type` 剔除）
