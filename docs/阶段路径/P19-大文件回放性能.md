# P19：大文件回放性能

> 阶段路径第 19 阶段。目标：把 200MB 级会话的回放从「打开即卡死、播放卡、拖不动」收敛到「可交互、播放流畅」。承接 P17（段控制上收与性能加固，已完成 Rust 侧主线程止血 `c2d159b`）。方案见 [大文件回放性能（方案）](../架构/大文件回放性能（方案）.md)。
>
> **进度**：🚧 归档（2026-09-10）。Phase A/B/C 落地 + 两轮 fresh subagent 独立复核 ✅（首轮 3 项严重发现已修复并复验）；Phase E（回归/文档/skill 回写）✅。余两项：**运行时验收**（需 app 内操作，步骤见 [测试流程](../测试/P19-测试流程.md) 场景 2-5）；**Phase D（录制档位）经用户决定延后**——价值取决于运行时体感，随时可独立做，采纳门不变（O2：体积增幅 ≤30%）。

## 目标 ★

P17 修掉了录制/写入侧的主线程阻塞，`c2d159b` 补掉了读命令的 Rust 主线程冻结；但**回放侧本身仍是「三个 O(全量)」的模型**：全量加载 → 全段建 Replayer → 每次定位全量重放。实测 172MB / 27 段 / 24,277 事件的真实会话，这三层叠加直接把回放变成不可用。

本阶段专治这一层，且是**当前最高优先级**（用户 2026-09-10 明确「按性能优先级最高做」）：性能取舍一律优先，`usePlayer`/Player 组件的既有形态让位于实测收益。

与主线的关系：不改录制产物格式、不改 bundle 契约、不改 Sink 接口、不改交错事件模型——**只改回放侧读取与驱动方式**。

## 范围 ★

1. **覆盖**：
   - Phase A 交互与同步止血：废弃播放中漂移阈值纠偏、seek 改「松手提交」、诊断信号流虚拟化、播放循环收敛
   - Phase B 读路径分段化：`read_session_meta`（段索引 O(段数)）+ `read_segment`（raw IPC 直拼，零 `Value` 树）+ server 路由 + `Backend` 接口
   - Phase C Replayer 懒建与回收：只为即将活跃的段建 Replayer，删 attach 期 `pause(0)` 全建
   - Phase E 回归 + 文档 + `rrweb-recording` skill 回写（证伪「方案 A」）
2. **不在本阶段**：
   - **录制档位 `checkoutEveryNms`（原 Phase D，2026-09-10 延后）**：A/B/C 后 seek 频率已收敛，其价值取决于运行时体感；随时可独立做，采纳门不变（同一场景对照录制、体积增幅 ≤30% 才上；`full` 档零 diff 红线不变）
   - 位置精确回放（原「方案 C」）——与性能无关，独立候选
   - 二进制事件编码（protobuf/msgpack）——先用直拼 + raw IPC 吃掉主要浪费
   - Worker 化（rrweb Replayer 依赖 DOM）
   - 录制端 `inlineStylesheet` 关闭——牺牲回放保真度
   - `HttpBackend` 迁移到新分段端点的消费方改造——端点先落地，消费方可后置

## 关键陷阱（可选，实施时发现）

- **`pause(0)` 的隐性代价**：rrweb 2.1.1 的 `pause(timeOffset)` 在传入数值时会走 `play(timeOffset)` 分支，即便 offset=0 也会完成「遍历全部事件 → 为每个未来事件建 castFn 并塞进 timer → 应用快照」的完整流程，随后立刻被 `PAUSE` 清空。删掉它是 Phase C 收益的一半。
- **`play(offset)` 是非 paused 状态下的「全量重放」**：见 rrweb `Replayer.play` 实现（非 paused 先发 PAUSE 再 PLAY），这是 D4 的立论基础，也是任何「用 play 做微调」想法的陷阱。
- **外部会话常常没有 `hidden` 事件、也没有 `endedAt`**（实测目标会话：27 个 `shown`、**0 个 `hidden`**、session.json 无 `endedAt`）。因此时间轴总时长的唯一来源是**段内最后一个事件的 timestamp**——这直接决定了段索引必须带 `lastTs`（首版方案只打算带首行的 width/height，实施中被真实数据推翻）。守则：任何「只读元信息」的设计都必须先拿真实会话验证字段可得性。
- **`seek` 在播放中原本会让画面停住**（潜在缺陷，P19 顺手修正）：旧 `seek()` 只对各段 `pause(offset)`，不改 `playing`；随后 tick 看到这些段已在 `active` 集合里，不会重新 `play` → 时钟继续走、画面不动。新实现在播放中 seek 会 `play(offset)` 续播。
- **⚠️ `activeAt()` 必须按 label 去重（首轮独立复核发现，P19 主症状的真正根因）**：`active` 集合来自 `activeByLabel.values()`（每 label 至多一段），而旧 `activeAt()` 返回**所有**满足 `absT >= shownAt && (hiddenAt === null || absT < hiddenAt)` 的段。当会话缺 `hidden` 事件时（本阶段的目标会话正是 27 `shown` / **0 `hidden`**），同一 label 的全部历史段都满足该条件 → `tick()` 判定它们"新激活"，**每 50 ms 对每段调一次 `play()`**（实测 13 次/tick）→ 每次都是一次 O(段首→offset) 全量重放，约 260 次/秒。这既推翻 1.0 的验收声明（"`play` 只在段激活时调用"），也意味着 **D4 想消灭的正反馈其实一直还在**，只是换了个入口。修法：`activeAt` 与 `syncVisibility` 同源，按 label 取 `shownAt` 最大者。
- **按需加载把两个"隐性语义"暴露成真问题**：① 信号流从"全量"退化为"仅已加载段"（诊断工具的功能回归）→ 补 `read_session_signals_json` 廉价全量路径；② 段回收后重载会**重复**并入其诊断信号（实测 3 秒内 1249 → 29,009 行，23,791 条重复）→ 加 `signalsCollected` 标志位。这两条都是"分段加载"引入的、原方案未预见的次生问题。
- **1.3 播放头未改 rAF（实施偏离，方案 §4.6 的例外）**：rAF 会把 Vue 更新频率从 20Hz 提到 60Hz（更新量 ×3），而瓶颈从来不是时钟频率；且 rAF 在窗口不可见时完全停摆，需额外 `visibilitychange` 重对齐。故保留 `setInterval(50)`，把预算花在 `syncVisibility` 的活跃集合 diff 上。**此偏离已在 /impl 预检中提出，用户未反对但未显式裁定；如后续实测显示播放头不顺滑，再切 rAF 并补重对齐。**
- **`MAX_LIVE_SEGMENTS` 用计数而非超时**：原方案写的是 `EVICT_AFTER_MS=30s` 超时回收，实施改为「挂载数 > 6 时淘汰离播放头最远的非活跃段」——超时需要一个额外的计时器，而计数淘汰在同一处（`ensureUpcoming`）就能完成，且直接约束了内存上界。
